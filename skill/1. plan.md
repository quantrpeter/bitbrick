# BitBrick: Development Plan

BitBrick is a web portal for designing custom pin-and-axle building parts (beams, frames, connectors, axles) in the browser and exporting them for 3D printing. Feature reference: [Part Designer](https://marian42.de/partdesigner/). Architecture reference: the `n` project (side-loaded React modules in Laravel) and `wps` (Docker production deployment, Google login).

> BitBrick is an independent project. Keep a short "not affiliated with any brand owner" line in the footer and use no third-party brand names, logos or product names anywhere in the UI, code, docs or URLs.

Verified so far: 22 PHP tests, 28 designer tests, and a headless-browser run of the whole flow (keyboard editing, undo,

dev-server side-loading modes.

Deviations from this plan, and why:
- **Share links use the URL hash** (`/designer#part=...`), not the query string. The hash is never sent to the server or logged.
- **The dev-server probe only runs in the `local` environment.** Probing `localhost:8095` for every visitor (as `n` does) would let anything listening on a visitor's own port inject script into the page.
- **Mesh worker is started from a blob** (`workerFactory.js`) because browsers refuse cross-origin Worker URLs, and the dev bundle comes from another origin. This needed a static `publicPath` and a single self-contained chunk.
- **Only measurements that change the geometry are exposed.** The reference tool lists a few more (for example pin lip size, attachment adapter); they will be added when the geometry uses them.
- **Share-link name field escapes `~`** because it is the field separator (found by a unit test).

## 1. Goals and non-goals

**Goals**
- Design a custom part in the browser with a block editor and a live 3D view.
- Export watertight, printable STL files that fit real pins and axles.
- Share designs by URL, and save them to a personal library after Google sign-in.
- Let advanced users tune tolerances for their printer and material.
- Run the same way in development (side-loaded) and production (Docker).

**Non-goals (v1)**
- General-purpose CAD or free-form modelling.
- Payments, marketplace, teams or classes.
- Native mobile apps.

## 3. Sideloading (same pattern as `n/network` and `n/blockly-microPython`)

### 3.1 How it works in `n`
1. The React app lives in its own folder (`n/network`) with its own `package.json` and `webpack.config.js`.
2. `npm run build` writes `bundle.js` straight into Laravel's `public/` (`../public/network-production`).
3. A Laravel Blade view (`resources/views/network.blade.php`) contains only `<div id="main"></div>` and a small loader script.
4. The loader first tries the **webpack dev server** (`http://localhost:8090/bundle.js`). If that fails (`onerror`), it falls back to the **built bundle** on disk (`/network-production/bundle.js`).
5. Laravel routes serve the page behind auth, with a catch-all `/{module}/{any}` route so deep links and F5 work.

Result: the page is served by Laravel (same origin, session cookie, CSRF token), while the JS comes from the hot-reloading dev server during development.

### 3.2 BitBrick layout

```
bitbrick/                      Laravel app root
  app/ routes/ resources/ database/ ...
  designer/                    React + Three.js app (own package.json, like n/network)
    src/
      index.html  index.js
      model/ geometry/ render/ state/ ui/ catalog/ export/ workers/
    webpack.config.js          output -> ../public/designer-production
  public/designer-production/  built bundle (committed or built in Docker, see 6.2)
  resources/views/designer.blade.php   loader (dev server first, built bundle fallback)
  docker/ Dockerfile docker-compose-prod.yml release.sh
```

### 3.3 Rules to copy
- **Dev server port:** pick one that does not clash with the `n` modules (`n/network` uses 8090, `n/blockly-microPython` uses 8082). Proposal: **8095**. Allow cross-origin with `Access-Control-Allow-Origin: *` and `historyApiFallback: true`.
- **webpack:** `library: { name: 'quantr', type: 'var' }` is only needed if the host page calls into the bundle. BitBrick does not need it, so drop it unless a Blade page uses it.
- **Dev vs prod output:** development writes to `designer/build` (so it never clobbers the production build); production writes to `public/designer-production`.
- **Blade view:** inject `<meta name="csrf-token">`, and pass the signed-in user, feature flags and API base URL through a small `window.__BITBRICK__` JSON object so the SPA needs no extra bootstrap request.
- **Improvement over `n`:** `n` appends `?rand()` to the bundle URL on every request, which defeats browser and CDN caching. Use the bundle file's mtime or a build hash instead: `?v={{ filemtime(public_path('designer-production/bundle.js')) }}`. This also avoids having to clear the CDN cache on each deploy.
- **Debug banner:** keep the small "Debug Mode" badge when the dev server is the source, so nobody mistakes a dev bundle for production.

### 3.4 Routes (order matters)

```php
Route::get('/', [AuthController::class, 'show'])->name('login');   // home page = login page (no /login)
Route::get('/auth/google', [GoogleLoginController::class, 'redirect']);
Route::get('/auth/google/callback', [GoogleLoginController::class, 'callback']);
Route::post('/logout', [AuthController::class, 'logout']);

Route::get('/p/{token}', [SharedDesignController::class, 'show']);   // public, read-only view

Route::middleware('auth')->group(function () {
    // CRUD API must be declared BEFORE the SPA catch-all
    Route::get('/designer/designs', [DesignController::class, 'index']);
    Route::post('/designer/designs', [DesignController::class, 'store']);
    Route::get('/designer/designs/{id}', [DesignController::class, 'show'])->whereNumber('id');
    Route::put('/designer/designs/{id}', [DesignController::class, 'update'])->whereNumber('id');
    Route::delete('/designer/designs/{id}', [DesignController::class, 'destroy'])->whereNumber('id');
});

Route::get('/designer', [DesignerController::class, 'index']);                 // SPA host
Route::get('/designer/{any}', [DesignerController::class, 'index'])->where('any', '.*');  // LAST
```

**Decided (reversed from the first draft):** nobody can use BitBrick without signing in. The original question was whether the editor is usable without signing in?
- **Yes: anonymous editing, URL sharing and STL export need no login. Saving to "My Designs" and publishing need Google login.** Lowest friction, best for growth.
- No: gate everything behind login, as `n` does with its auth middleware.

## 4. Google login (Gmail accounts)

Follow `wps`: `app/Http/Controllers/Auth/GoogleLoginController.php` with Laravel Socialite.

**Flow**
1. User clicks "Sign in with Google" and goes to `/auth/google`, which redirects to Google.
2. Google redirects back to `/auth/google/callback`.
3. The callback finds the user by `google_id`, then by `email`, otherwise creates one. It then calls `Auth::login($user, remember: true)` and redirects to the intended URL (default `/designer`).

**Setup checklist**
- Create a **new** OAuth client in Google Cloud Console just for BitBrick. Do not reuse the `wps` client.
- Authorized redirect URIs: `http://localhost:8000/auth/google/callback` (dev) and `https://<production-domain>/auth/google/callback` (prod).
- `composer require laravel/socialite`.
- `config/services.php`: `google.client_id`, `google.client_secret`, `google.redirect`, all from `.env`.
- Add the OAuth consent screen with app name, logo, privacy policy URL and scopes `openid email profile` only.

**Users table additions:** `google_id` (unique, nullable), `avatar` (nullable), `email_verified_at`, `role` (`user` or `admin`), `status` (`enabled` or `disabled`, like `n`). No password column is needed. Use a random hash or nullable.

**Security**
- Handle `InvalidStateException` with a friendly "login expired, try again" message (as `wps` does).
- Only trust the email if Google reports it as verified.
- Regenerate the session ID after login. Logout is POST + CSRF.
- Rate-limit `/auth/*`.
- Do not `dd($ex)` in the callback (the `n` Google controller does); log the error and redirect to `/login`.
- Optional allow-list or domain restriction via an env var for private beta.

## 5. Data model

### 5.1 Part (client-side, also stored as JSON)

```ts
type BlockType = 'pinHole' | 'axleHole' | 'pin' | 'axle' | 'solid' | 'ballJoint';
type Axis = 'x' | 'y' | 'z';

interface Block {
  pos: [number, number, number];   // integer grid coords (half steps allowed)
  type: BlockType;
  axis: Axis;
  size: 'full' | 'half';
  rounded: boolean;
}

interface Part {
  version: number;                 // schema version, for URL and DB compatibility
  name: string;
  blocks: Block[];
  measurements: Partial<Measurements>;   // overrides only, defaults live in code
}
```

### 5.2 Database

| Table | Columns |
|---|---|
| `users` | id, name, email (unique), google_id (unique), avatar, role, status, timestamps |
| `designs` | id, user_id (FK), name, data (JSON, the `Part`), schema_version, thumbnail (path or data URL), is_public, share_token (unique, nullable), timestamps |
| `design_exports` (later) | id, design_id, format, created_at, for usage metrics |
| `sessions`, `cache`, `jobs` | Redis in production, Laravel defaults otherwise |

### 5.3 URL sharing
Compact, readable, versioned text in the URL hash: `/designer#part=v1~<name>~<x.y.z.TAS_...>~<measurement overrides>` (see `designer/src/model/codec.js`). If it exceeds about 8,000 characters, fall back to a saved design with `/p/{share_token}`.

## 6. Production: Docker (modelled on `wps/docker-compose-prod.yml`)

### 6.1 Services

| Service | Image | Purpose | Host port (proposal) |
|---|---|---|---|
| `app` | `quantrpeter/bitbrick:1.0` | nginx + php-fpm + queue + scheduler under supervisord | `8003:80` |
| `mysql` | `mysql:8.4` | Database, with healthcheck | `33309:3306` (or none) |
| `redis` | `redis:7-alpine` | Session, cache, queue, with healthcheck | `6381:6379` (or none) |

Host ports must not clash with `wps` on the same server (it uses 8002, 2222, 33308, 8008, 6380). Prefer **no host port at all** for MySQL and Redis in production, since only `app` needs to reach them.

Left out on purpose compared with `wps`: Meilisearch (no search in v1), phpMyAdmin (use a one-off container or SSH tunnel when needed), Stripe, xAI and Threads variables.

### 6.2 Image (copy `wps/Dockerfile`, add one stage)

1. **vendor stage:** `composer install --no-dev --optimize --classmap-authoritative`.
2. **assets stage:** Laravel Vite assets, if any (only the landing and login pages).
3. **designer stage (new):** `node:22-alpine`, `cd designer && npm ci && npm run build` produces `public/designer-production`. Copy that into the runtime image. This replaces the manual "run build, upload `public/...`, clear CDN cache" step from the `n` README.
4. **runtime stage:** `php:8.4-fpm-bookworm` with `pdo_mysql`, `bcmath`, `intl`, `opcache`, `gd`, `zip`, `phpredis`, nginx, supervisor.

Entry point (same as `wps/docker/entrypoint.sh`): wait for DB, `migrate --force`, `storage:link`, then `config:cache`, `route:cache`, `view:cache`. Add the nginx rule that serves `/designer-production/*` as static files with long cache headers, since the URL is versioned by hash.

Build and push with `buildx` for `linux/amd64,linux/arm64`, like `wps/release.sh`.

### 6.3 Environment (names only, values in an untracked `.env.prod`)

`APP_NAME`, `APP_ENV=production`, `APP_KEY`, `APP_DEBUG=false`, `APP_URL`, `LOG_CHANNEL`, `DB_*`, `REDIS_*`, `SESSION_DRIVER=redis`, `QUEUE_CONNECTION=redis`, `CACHE_STORE=redis`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`, `TRUSTED_PROXIES`.

**Do not copy the secrets from `wps/docker-compose-prod.yml`.** That file holds live credentials in plain text: Stripe live keys, Google client secret, API keys, a root SSH password and the DB passwords. If it is in git or shared anywhere, rotate those keys. For BitBrick:
- Keep `docker-compose-prod.yml` free of secrets and use `env_file: .env.prod` (git-ignored) or Docker secrets.
- Generate new `APP_KEY`, DB passwords and Google credentials.
- Commit only `.env.prod.example`.

### 6.4 Hardening and operations
- **Drop SSH in the container.** `wps` runs `sshd` with an optional root password to sync code. For BitBrick ship code only through the image (`docker compose pull && up -d`).
- Run PHP as `www-data`, `read_only` root filesystem where possible, and mount only `./bitbrick-storage`.
- TLS terminates in front (Cloudflare or a reverse proxy). Configure Laravel `TrustProxies` so `https` and the real client IP are correct, and set `SESSION_SECURE_COOKIE=true`.
- Queue workers: `default` only for v1 (thumbnails and exports can use it). Add a `thumbnails` queue later if needed.
- Backups: nightly `mysqldump` plus a copy of `./bitbrick-storage`. Test a restore before launch.
- Logs to stderr (`LOG_STACK=single,stderr`), so `docker logs` works.
- Healthcheck endpoint `/up` (Laravel default) wired into compose.

## 7. Architecture of the React app

```
designer/src/
  model/        Part, Block, Measurements, defaults, validation (no DOM, no Three.js)
  geometry/     per-block-type mesh generators, boolean ops, STL writer (no DOM)
  render/       Three.js scene, cursor gizmo, picking, display styles
  state/        store, undo/redo, URL sync, local autosave
  ui/           panels: Part, EditBlock, Catalog, Measurements, Library, About
  api/          fetch wrapper for the Laravel API (CSRF header, error handling)
  catalog/      preset parts (JSON) and generated thumbnails
  export/       STL, then 3MF and LDraw
  workers/      mesh.worker.js
```

Rules:
- `model/` and `geometry/` do not depend on the DOM or Three.js, so they are unit-testable in Node.
- The UI never builds meshes. It sends a `Part` to the worker and receives buffers.
- One source of truth, the `Part` object. The URL, autosave and undo all derive from it.
- The React router uses the `/designer/*` base path and relies on the Laravel catch-all.

## 9. Development phases

### Phase 0: Foundation (about 3-4 days)
- Laravel scaffold, MySQL and Redis in a **dev** `docker-compose.yml`, `.env.example`.
- `designer/` React + webpack skeleton, `designer.blade.php` loader (dev server first, built bundle fallback), `/designer` and `/designer/{any}` routes.
- Google login end to end (Socialite, `users` migration), `/login` page, logout.
- First production image build and a `docker-compose-prod.yml` that boots on the server with a placeholder page.
- **Done when:** sign in with Google on the production domain, then see an empty orbit-able 3D scene served through the side-loaded bundle.

### Phase 1: Block editor MVP (about 1 week)
- Grid, cursor gizmo, keyboard cursor movement.
- Place and remove blocks. Type, orientation, size and edges via panel and shortcuts.
- Placeholder geometry (boxes and cylinders) to validate interaction.
- **Done when:** a 5 x 7 frame can be built with the keyboard only.

### Phase 2: Real part geometry (about 1-2 weeks, the hardest part)
- Generators for pin hole (counterbore, offset), axle hole (cross), pin (lips), axle, solid and ball joint.
- Rounded and non-rounded edges, interior cavities and end margins.
- Merge blocks into one manifold mesh with boolean union and subtract in the worker.
- **Done when:** exported meshes are manifold with no inverted normals, and pass the validator.

### Phase 3: Measurements and tolerances (about 3-4 days)
- Measurements panel, per-field Reset, global Reset and Apply, validation.
- Printer presets (FDM 0.4 mm, resin, SLS).
- **Done when:** a value change regenerates a typical part in about 1 s or less.

### Phase 4: Save, share and export (about 1 week)
- Save STL (binary), named after the part.
- URL share encoding with round-trip tests, `/p/{token}` public view.
- "My Designs": list, open, rename, duplicate, delete, thumbnails. Autosave drafts to localStorage before login.
- After login, offer to import the local draft into the library.
- LDraw export, then 3MF.
- **Done when:** a shared link reproduces the identical part in a fresh browser.

### Phase 5: Catalog (about 3-4 days)
- Preset parts as JSON, thumbnails generated at build time.
- **Done when:** there are at least 40 presets, with search.

### Phase 6: Polish and launch (about 1 week)
- Display styles (Contour, Solid, Wireframe, X-ray), responsive layout, touch controls.
- Accessibility, shortcut help overlay, onboarding tour, empty states.
- Privacy policy and terms (required for the Google consent screen), cookie notice if analytics are used.
- Performance pass, error reporting, backups verified, rollout.
- **Done when:** Lighthouse above 90 and testers complete a first part with no help.

## 10. Testing and quality

- **PHP (Pest or PHPUnit):** Google callback with Socialite mocked (new user, existing email, existing `google_id`, invalid state), design CRUD authorization (a user cannot read or edit another user's private design), share token access.
- **JS unit (Vitest or Jest):** serialization round-trip (fuzzed), measurement validation, block-to-mesh checks.
- **Geometry:** watertight, positive volume, no self-intersection, bounding box matches the grid.
- **Golden files:** STL hashes for reference parts to catch regressions.
- **Physical fit:** print a calibration plate (pin hole 4.8 to 5.1 mm, axle holes) and verify with real pins and axles from your own parts. Feed results back into defaults.
- **E2E (Playwright):** log in with a test user, build, save, share, reload, export.
- **Deployment smoke test:** `docker compose up` from an empty volume, check migrations, `/up`, login redirect, the bundle URL returns 200, and the dev-server fallback path works.

## 11. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Boolean ops produce non-manifold meshes | Unprintable STL | `manifold-3d`, a validator, and block export with a clear message |
| Printer tolerances vary | Parts do not fit | Printer presets and a calibration plate generator |
| Dev-server fallback hides a missing production bundle | Blank page in production | CI check that `public/designer-production/bundle.js` exists in the image, and a smoke test |
| Stale bundle in browser or CDN | Users run old code | Hash or mtime in the bundle URL instead of `rand()` |
| Secrets committed with the compose file | Credential leak | `.env.prod` outside git, new keys per project, rotate the `wps` ones |
| Google OAuth misconfiguration (redirect URI, consent screen not published) | Login fails for users | Checklist in section 4, test on the production domain before launch |
| Long URLs when parts grow | Sharing breaks | Compact encoding and saved-design short links |
| Brand or trademark issues | Legal | Neutral naming everywhere, footer disclaimer, review before launch |
| Slow mesh rebuild on large parts | Laggy UI | Worker, per-block caching, debounce |

## 12. How BitBrick can be better than the reference tool

**Quick wins (v1 if possible)**
1. Undo/Redo and a saved library. The reference has no accounts, so users lose work.
2. Printer-aware presets and a printable calibration plate instead of guessing six tolerance numbers.
3. Multi-select, copy/paste, mirror and rotate.
4. Mouse-first editing (click a face to add, drag to extrude, right-click to delete), with keyboard shortcuts kept for power users.
5. Onboarding tour and starter templates.

**Medium effort**
6. Live fit check with a ghost pin or axle and a clearance heat map.
7. Section view, ruler and part dimensions.
8. Print readiness report: overhangs, thin walls, suggested orientation.
9. More export formats: 3MF, OBJ, LDraw.
10. Public gallery with fork and remix.

**Longer term**
11. Parametric templates ("beam, N holes, bend angle").
12. Assembly preview with several parts.
13. Live collaboration.
14. PWA and offline.
15. Open-source the project.

**How this plan can be better**
- Add **success metrics**: for example, 80% of new users export an STL in the first session, and the median time to first part is under 5 minutes.
- Pick the **target user** (home printing hobbyists, builders, educators). It decides the catalog, language and presets.
- Add owners, dates and a budget. The estimates above are one developer's guess.
- Write a **geometry spec** with exact dimensions and drawings for each block type before Phase 2, because that is where most bugs will come from.
- Decide a **license for exported designs** and a policy for public uploads.
- Add a **staging environment** (second compose project on another port) before the first public deploy.
- Decide **analytics and privacy** upfront: what is stored about Google users, how to delete an account, and where the data lives.
